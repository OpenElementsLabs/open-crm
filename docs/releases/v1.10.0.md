# Open CRM v1.10.0 – Release Notes

**Released:** 2026-07-15
**GitHub release:** [v1.10.0](https://github.com/OpenElementsLabs/open-crm/releases/tag/v1.10.0)
**Previous version:** [v1.9.0](https://github.com/OpenElementsLabs/open-crm/releases/tag/v1.9.0) (2026-06-26)

This is a **feature-heavy** release focused on getting contact data *into* the
CRM and making the app easier to run and install. It adds **CSV import** and
**single-contact enrichment** (Gravatar, Dropcontact, Cognism) for filling in
contact details, turns the frontend into an **installable PWA**, and ships an
**admin backup page** backed by a new backup sidecar service. It also surfaces
**HEIC decoding availability** in the admin area and extends the (still
optional, still off-by-default) MCP server with **image tools**.

There are **no database migrations** in this release. Operators **do** need to
read the **Upgrade notes**: the database-backup service has been replaced and
its environment variables were **renamed** — the old `S3_*` / `AWS_*` /
`BACKUP_CRON` variables no longer work.

---

## Highlights for Admins and Users

### Import contacts from a CSV file

`APP-ADMIN` and `IT-ADMIN` users can now **bulk-import contacts from a CSV
file** — ideal after a trade show or conference when you come back with a stack
of scanned business cards exported as a spreadsheet.

The import is a guided dialog in the contacts view: **upload → map columns →
preview → commit → result**.

- **Any column layout works.** You map each source column onto one of eight
  contact attributes (title, first name, last name, email, position, phone,
  LinkedIn URL, website URL). Columns you don't map are simply dropped.
- **First name and last name are required** mappings; the import won't start
  without them.
- **Partial success.** Rows are committed one by one, so a single bad row does
  not abort the whole file. You get a summary with per-row failure reasons and
  can **download a failure CSV** to fix and re-upload.
- Limits: files up to **20 MB / 5 000 rows**, comma- or semicolon-delimited,
  with a selectable text encoding.

Note: v1 does **not** deduplicate (email is not unique), and it does **not** map
companies or tags — those are follow-ups.

### Enrich a single contact from Gravatar, Dropcontact or Cognism

Admins can now **enrich an individual contact** from an external service to fill
in missing details — a photo, email, job position, LinkedIn link, or company.

- **Preview before anything is written.** Enrichment is read-only until you
  press **"Übernehmen"**. You always see exactly which fields would change.
- **Only empty fields are filled** — existing values are never overwritten.
- **All-or-nothing** apply (the one exception: creating a *new* company requires
  a separate opt-in checkbox).
- Three concrete integrations: **Gravatar** (photo, no key required),
  **Dropcontact**, and **Cognism**. Dropcontact and Cognism require an
  **IT-Admin** to configure API keys in the admin settings; Gravatar works out
  of the box.

⚠️ **Data-protection prerequisite.** Do **not** switch on Dropcontact or Cognism
before the legal groundwork is in place — a Legitimate-Interest Assessment
(Art. 6(1)(f) GDPR), data-processing agreements (Art. 28) with the provider, and
the Art. 14 information of the data subjects. These are operational/legal steps
outside the software. Gravatar (avatar lookup by email hash) has a lighter
footprint but should still be reviewed. See `docs/specs/110-contact-enrichment/`
for details.

### Install Open CRM as an app (PWA)

The frontend is now an **installable Progressive Web App**. On Chrome, Edge and
Android you'll get an **install affordance in the sidebar footer**; on iOS
Safari a short "Add to Home Screen" hint is shown. Once installed, Open CRM
launches in its **own window with its own icon and no browser address bar**.

- After every deploy you always get the **fresh** app — the app shell is never
  stale-cached.
- Opening the installed app **without a network connection** shows a branded,
  bilingual **offline page**.

Please note: this is **installability only — there is no offline access to CRM
data.** Only a static offline page is cached; everything else still requires a
network connection.

### Backup administration page (IT-Admin)

A new **`/admin/backup`** page lets an **IT-Admin** manage database backups
directly from the UI during the current testing phase:

- See the **backup service health** and metadata.
- **Trigger** a backup on demand.
- **List** existing backups and **download** a backup file.

This page talks to a **new backup service** that runs alongside the app (see
*Upgrade notes* — this replaces the previous cron-only backup container and
changes the required environment variables). If no backup token is configured,
the backend still boots and the page simply reports **"not configured."**

### HEIC support status in the admin area

The admin **`/admin/status`** page now shows whether **HEIC image decoding** is
actually available in the running container. A **green** indicator means HEIC
uploads will work; a **red** warning (with a tooltip pointing at the Dockerfile)
means `libheif` is missing and HEIC uploads will be rejected with a `415`.
Previously this was only visible as a startup log line — now operators can
verify it at a glance after a deploy.

### MCP: fetch contact photos and company logos (MCP only)

For those running the optional MCP server (introduced in v1.9.0, still **off by
default**), two new read-only tools — **`get_contact_photo`** and
**`get_company_logo`** — return the stored image as a proper MCP image result.
Previously an AI assistant could only see *whether* a contact/company had an
image, not the image itself. This changes nothing if you have not enabled the
MCP server.

## Other changes under the hood

These changes are not directly visible to end users:

- **New backup sidecar service.** The home-grown `./scripts` cron container was
  replaced by the published
  [`db-backup-service`](https://github.com/OpenElementsLabs/db-backup-service)
  image (`ghcr.io/openelementslabs/db-backup-service`, pinned by tag **and**
  digest). It exposes an HTTP API that the backend's `DbBackupClient` proxies via
  `/api/admin/backup/*` (all endpoints gated to `IT-ADMIN`).
- **Meilisearch now has a Docker health check.** The v1.10 image is
  Alpine-based and ships `curl`, so the backend now waits for Meilisearch to be
  genuinely `healthy` (not just started) before boot.
- **Startup ordering hardened.** The backend now depends on both Meilisearch and
  the backup service being `service_healthy`.
- **New backend dependency** `commons-csv` for CSV parsing; concrete
  enrichment clients (Gravatar/Dropcontact/Cognism) with their own DTOs and
  endpoints (no generic provider SPI by design).
- **MCP image-result path** added to the reusable
  `com.openelements.spring.base.mcp` layer so future tools/apps can return
  images too.
- **Frontend libraries bumped** — `@open-elements/nextjs-app-layer` and
  `@open-elements/ui` (the HEIC status uses a new generic "runtime
  capabilities" panel in the shared library).

## Upgrade notes

### ⚠️ Backup service replaced — environment variables renamed

The database-backup container changed from a home-grown cron script to the
`db-backup-service` HTTP API. **The old backup environment variables no longer
have any effect.** If you had backups configured, you must migrate them:

| Old (v1.9.0 and earlier) | New (v1.10.0)                     |
| ------------------------ | --------------------------------- |
| `S3_BUCKET`              | `DB_BACKUP_S3_BUCKET`             |
| `S3_PREFIX`              | `DB_BACKUP_S3_PREFIX`            |
| `S3_ENDPOINT`            | `DB_BACKUP_S3_ENDPOINT`          |
| `AWS_ACCESS_KEY_ID`      | `DB_BACKUP_AWS_ACCESS_KEY_ID`    |
| `AWS_SECRET_ACCESS_KEY`  | `DB_BACKUP_AWS_SECRET_ACCESS_KEY`|
| `AWS_DEFAULT_REGION`     | `DB_BACKUP_AWS_DEFAULT_REGION`   |
| `BACKUP_CRON` (cron)     | `BACKUP_INTERVAL` (e.g. `24h`)   |

Additionally, **two new variables** are required for the admin backup page to
work:

- **`DB_BACKUP_API_TOKEN`** – a bearer token shared between the backup service
  and the backend. Generate a strong random value, e.g. `openssl rand -hex 32`.
  **Leave it blank to run without backups** — the backend still boots and the
  admin backup page shows "not configured".
- **`DB_BACKUP_BASE_URL`** – the backend's URL to reach the backup service;
  already set to `http://db-backup:8080` in the provided `docker-compose.yml`.

The endpoint host and region must match (e.g. `fsn1.*` ⇄ `fsn1`). The provided
`docker-compose.yml` and `.env.example` are already updated with these names and
safe defaults; copy the new keys into your own `.env`.

### No database migrations

**No Flyway migrations run in this release.** The CSV import creates ordinary
`ContactEntity` rows through the existing save path, and none of the new
features add or change any tables or columns. The schema is unchanged from
v1.9.0.

### No new infrastructure to provision yourself

The backup service is the only container change and is already wired into
`docker-compose.yml`. There are **no** other new services — the PWA, enrichment,
CSV import, HEIC status and MCP image tools all run inside the existing
backend/frontend. If you run behind a reverse proxy, no new routes need to be
exposed (the service worker and offline page are served by the existing
frontend).

### Configuration / compatibility

- Existing **SSO, Brevo, translation, search and MCP** configuration remain
  fully compatible and unchanged.
- **Enrichment is off until configured.** Dropcontact/Cognism do nothing until
  an IT-Admin sets their API keys; Gravatar needs no key. ⚠️ Do not enable
  Dropcontact/Cognism before completing the GDPR prerequisites above.
- **PWA:** browsers may cache the previous (non-PWA) frontend; a normal reload
  picks up the new service worker. No action required.
