# Open CRM v1.11.0 – Release Notes

**Released:** 2026-08-28
**GitHub release:** [v1.11.0](https://github.com/OpenElementsLabs/open-crm/releases/tag/v1.11.0)
**Previous version:** [v1.10.0](https://github.com/OpenElementsLabs/open-crm/releases/tag/v1.10.0) (2026-07-15)

This release adds **Opportunities** — the first sales-pipeline entity in Open CRM
— alongside a set of smaller improvements: **per-page browser titles and link
previews**, a **HEIC-decoding status indicator** in the admin area, and a
**shorter, more resilient login session**. It also brings three Open Elements
dependencies up to date, one of which is **breaking at the database level**.

> ⚠️ **Operators must read the Upgrade notes before deploying.** This release
> runs **two** Flyway migrations. `V35` creates the new opportunity tables and is
> harmless. `V36` **moves seven existing database tables into a new schema**
> (`oe_spring_services`) and is a **stop-the-world** upgrade: it is not safe for
> rolling deploys, a backup must be taken **before** the deploy, and a tested
> rollback path is provided. Coolify's replace-then-start model already satisfies
> the downtime requirement — **do not switch this release to a rolling deploy
> strategy.**

> ℹ️ **Note on v1.10.0's notes.** The v1.10.0 release notes mention the HEIC
> decoding indicator in the admin area. That work actually landed **after** the
> `v1.10.0` tag was cut and ships here, in v1.11.0. The v1.10.0 file is left
> unchanged as a historical record.

## Highlights for Admins and Users

### Opportunities — track deals, not just contacts

Open CRM now has a dedicated **Opportunities** section, reachable from the
sidebar. Until now the CRM could record *who* you know; it could not record
*what you are selling them*. An opportunity ties a deal to a company and the
people involved, so pipeline work stops living in spreadsheets and inboxes.

Each opportunity has:

- a **title**, and a required **company** plus a required **main contact** —
  every deal has an owner organisation and a primary counterpart;
- any number of **additional contacts**, for the other people involved on the
  customer side;
- a **status** — `OPEN`, `WON` or `LOST`, starting at `OPEN`;
- a free-text **stage** and free-text **product**, both offered as comboboxes
  that suggest values already in use, so the team converges on a vocabulary
  without the system forcing one;
- an optional **estimated value in EUR** — the first monetary field in Open CRM,
  stored with two decimal places and formatted in the list view;
- a required **owner**, the internal user responsible for the deal, defaulting to
  whoever creates it. This is the first time a business record is assigned to a
  named colleague.

Opportunities behave like the entities you already know: they carry **tags** and
**comments**, they appear in **global search**, they show up in the **Updates**
feed when someone changes them, and the tag list counts them.

**Why "stage" is free text.** Stage is deliberately not a fixed list. The Open
Elements Kanban app will become the leading source for stage and status, and a
free-string field lets that integration set whatever values the board uses
without a database migration on each change. Until that integration exists,
stage and status are maintained by hand.

**Permissions.** Any signed-in user can read, **create and edit** opportunities
and write comments on them. **Deleting** an opportunity — or deleting any
comment on one — requires `APP-ADMIN`.

**MCP.** If you run the optional MCP connector, three read-only tools were added:
`list_opportunities` (with search/status/stage/company/contact/owner/tag
filters), `get_opportunity`, and `list_opportunity_comments`.

> ⚠️ **Behaviour change: some deletions are now refused.** A company that is
> referenced by an opportunity, and a contact that is the **main contact** of an
> opportunity, **can no longer be deleted** — the attempt fails with a conflict
> error and an explanatory message. Being an *additional* contact does not block
> deletion. This protects deals from losing their company or counterpart, but it
> also means a GDPR erasure request against such a contact now requires
> reassigning or deleting the opportunity first. A proper anonymisation flow is
> planned to replace this interim rule before wider production use.

### Meaningful browser tabs and link previews

Contact and company detail pages now carry their own HTML metadata instead of
the generic app-wide title. A tab, bookmark or history entry for a contact reads
**"Open CRM: Max Mustermann"** rather than just "Open CRM", which makes a row of
open tabs usable again.

Pasting such a link into a chat also produces a proper preview card: the entity's
description is used as the summary, and a generated 1200×630 image frames the
contact's photo or the company's logo in Open Elements branding, falling back to
the person's or company's initials when no image is stored.

**These pages remain behind the login.** The preview tags are metadata hygiene,
not public reach — the pages are not exposed to unauthenticated visitors, and the
app is marked `noindex` so search engines do not attempt to list it. A chat
service that has no session simply shows a plain link, as before.

### HEIC upload support is now visible in the admin area

Contact photos taken on an iPhone (HEIC) are decoded by a native library that
must be present in the running container. Previously the only way to know whether
it shipped correctly was to read the backend startup log — or to wait for a user
to hit an "unsupported format" error.

The **admin status page** now shows a capability row for HEIC decoding: green
when decoding is available, red with a "check Dockerfile" hint when it is not.
An `IT-ADMIN` can confirm at a glance after every deploy that the native
dependency is intact. The check is fail-safe: if the status cannot be determined,
it reports as unavailable rather than claiming support that is not there.

### Shorter, more resilient login session

`@open-elements/nextjs-app-layer` changes session behaviour:

- The login session now lasts **8 hours** instead of 30 days. In practice users
  re-authenticate roughly **once per working day** — normally a silent Authentik
  SSO round-trip, not a fresh password entry. This fixes a real defect: the old
  30-day cookie outlived the OIDC refresh token, so the app could believe you
  were logged in while every API call quietly failed.
- A dead/revoked refresh token now cleanly redirects to **`/login`** instead of
  dropping you into an app shell whose requests all fail.
- Transient identity-provider hiccups (5xx, network errors, timeouts) no longer
  log you out — the session only ends once the token has genuinely expired.

No user action is required; users will simply be asked to log in about once a day.

## Other changes under the hood

### Dependency updates

| Dependency | From | To | Nature |
|---|---|---|---|
| `com.open-elements:java-parent` | 1.0.0 | 1.2.1 | Build-only — no runtime effect |
| `com.open-elements:spring-services` | 1.2.0 | 1.3.1 | **Coordinate + database schema change** |
| `@open-elements/nextjs-app-layer` | 0.5.0 | 0.7.1 | Admin status page extensions; session + OIDC refresh hardening |
| `@open-elements/ui` | 0.8.0 | 0.9.0 | Capability-status component used by the admin page |

No Spring Boot, Testcontainers, `next`, `next-auth` or React version moves with
this release.

### `spring-services` is now modular

The library became a Maven reactor. Open CRM now consumes the à la carte modules
it actually uses — `spring-services-core`, `-search` and `-dbbackup` — via the
`spring-services-bom`. The MCP, Slack and email modules are deliberately not
pulled in; Slack and mail client libraries leave the classpath as a result. Open
CRM keeps its own MCP implementation for now, because it contains image tools the
library module does not yet have.

### New API endpoints

- `GET`/`POST`/`PUT`/`DELETE` `/api/opportunities` and
  `/api/opportunities/{id}/comments` — opportunity CRUD and comments.
- `GET /api/users/options` — the lightweight user list used by the owner selector.
- `GET /api/admin/capabilities` — runtime capability report (`IT-ADMIN` only),
  backing the HEIC status row.

### A real release process for the application

Until this release, the versions in the build files were never maintained:
`backend/pom.xml` still claimed `0.1.0-SNAPSHOT` and `frontend/package.json`
`0.1.0`, eleven releases in. Both now carry the true application version, and
the repository gained the tooling to keep it that way:

- `check-versions.sh` runs on **every pull request** and fails if the backend and
  frontend versions differ or if the version was downgraded below the latest
  release tag.
- `release.sh` prepares a release locally — it verifies preconditions (including
  that the release notes exist), builds backend, frontend and all Docker images,
  then commits, tags and bumps to the next snapshot.
- A tag-triggered workflow re-builds the tagged tree from a clean checkout and
  publishes the GitHub Release, using this file as the release body.

For anyone self-hosting Open CRM, the practical consequence is a guarantee:
**a tag that has no published GitHub Release is not approved for deployment.**
Deploy a released tag, never `main`. The full procedure is documented in
[`docs/release.md`](../release.md).

## Upgrade notes

### ⚠️ Planned downtime — database schema migration (`V36`)

Two migrations run on startup:

- **`V35`** creates the new `opportunities`, `opportunity_contacts`,
  `opportunity_tags` and `opportunity_comments` tables. It only adds tables and
  needs no special handling.
- **`V36`** moves `spring-services`' seven tables — `users`, `api_keys`,
  `audit_log`, `comments`, `settings`, `tags`, `webhooks` — out of the `public`
  schema into a dedicated **`oe_spring_services`** schema.

The move is **data-preserving**: it relocates the tables (with all their data,
indexes and foreign keys) — it does not recreate them. The foreign keys that
point from CRM tables (opportunities, the `*_tags` and `*_comments` join tables)
into these tables remain valid as cross-schema references.

Because the instant `V36` runs the old `public.<table>` names disappear, a still
-running old instance would break. **This upgrade must be stop-the-world.**

### Deploy procedure (in order)

1. **Take a backup first, through the *running* old version.** Open
   **`/admin/backup`** on the current (v1.10.0) deployment and trigger a backup.
   Taken before the container is replaced, its dump reflects the pre-migration
   `public` layout and a matching `flyway_schema_history`.
2. **Deploy v1.11.0** in Coolify. The container is replaced (not run alongside
   the old one), the new backend boots, and Flyway applies `V35` and `V36`.
3. **Run the smoke checks** below.

### Smoke checks after deploy

- **Login** — OIDC round-trip against Authentik succeeds (new 8-hour session).
- **Search** — global search returns results, including the new Opportunities
  section.
- **Comments** — create and read a comment.
- **Audit log** — the audit view lists entries and records a new action.
- **Opportunities** — the list loads, and an `APP-ADMIN` can create one against
  an existing company and contact.
- **Admin status** — the page loads and shows the HEIC capability row.
- **`/admin/backup`** — reports the sidecar healthy and lists backups.
- **MCP** — if enabled, the connector still answers.
- **Post-migration backup** — trigger a **fresh** backup and confirm the dump
  contains the seven `oe_spring_services` tables **with their data**. If it does
  not, treat it as a **release blocker** (see below) and roll back.

### Rollback

If v1.11.0 fails to boot **after** `V36` has run, recover — do **not** try to
`git revert`:

1. Roll the app image back to **v1.10.0** in Coolify (don't let it start yet, or
   accept that its first start fails until step 2 completes).
2. Run **`docs/specs/115-dependency-updates/rollback.sql`** against the
   production database as the owner role. It moves the seven tables back to
   `public`, drops the empty `oe_spring_services` schema, and **deletes the `V36`
   row from `flyway_schema_history`** — that last step is not optional: without
   it the v1.10.0 jar aborts at startup with *"Detected applied migration not
   resolved locally: 36"*.
3. Delete the `V35` row from `flyway_schema_history` as well, for the same
   reason. The opportunity tables themselves can be left in place — v1.10.0 does
   not know about them and ignores them — or dropped once you are certain no
   opportunity data is worth keeping.
4. Start v1.10.0 and re-run the smoke checks.

Restoring the pre-migration dump from step 1 of the deploy is the fallback of
last resort, since it discards anything written after the backup — including any
opportunities created since.

**Rehearse `rollback.sql` on the Coolify dev instance before the production
deploy.** Follow the step-by-step checklist in
**`docs/specs/115-dependency-updates/rollback-rehearsal.md`**. (Note: dev holds
independent throwaway data, so the rehearsal validates the DDL and mechanics but
not behaviour against production row counts.)

### Data-protection note: deletions can now be refused

As described above, deleting a company referenced by an opportunity, or a contact
that is an opportunity's main contact, now fails with a conflict. If your erasure
process assumes a contact can always be deleted, it needs an extra step:
reassign or delete the opportunity first. Plan for this before the first erasure
request arrives after the upgrade.

### Operator action: verify the Authentik access-token lifetime

The frontend polls the session roughly every **120 s**. If Authentik issues
**very short-lived** access tokens (under ~2 minutes) for the `open-crm` client,
the browser may not notice an expired session promptly. **Check the client's
access-token lifetime in Authentik.** If it is under two minutes, a follow-up is
needed to pass a shorter `refetchInterval` to the frontend; at two minutes or
more, no change is required. This is a runtime configuration check that cannot be
verified from the code.

### Local development note

Backend DB tests reuse a Testcontainers PostgreSQL container. A reused container
that has already applied `V35`/`V36` will fail Flyway validation if you check out
a **pre-v1.11.0** branch. If that happens, remove the reused container and let a
fresh one start.

### No infrastructure changes; two new (optional) env vars

There are no new services and no `docker-compose.yml` changes. The production
database role is the schema owner, so no additional `CREATE SCHEMA` / grant steps
are required.

The `spring-services` 1.3.x modules are now activated by explicit flags, so two
new optional environment variables exist — **both default to `true`, so no action
is required** to keep current behaviour:

- **`MEILI_ENABLED`** (default `true`) — activates the global-search module.
- **`DB_BACKUP_ENABLED`** (default `true`) — activates the backup client so
  `/admin/backup` works. A blank `DB_BACKUP_API_TOKEN` still reports "not
  configured" exactly as before; this flag only controls whether the client is
  wired at all. Set to `false` only to remove the backup module entirely.

### Configuration / compatibility

- Existing **SSO, Brevo, translation, search and MCP** configuration remains
  fully compatible and unchanged.
- **No new routes** need to be exposed on a reverse proxy; opportunities and the
  generated preview images are served by the existing frontend and backend.
