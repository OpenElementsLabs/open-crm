# Open CRM v1.12.0 – Release Notes

**Released:** 2026-09-29
**GitHub release:** [v1.12.0](https://github.com/OpenElementsLabs/open-crm/releases/tag/v1.12.0)
**Previous version:** [v1.11.0](https://github.com/OpenElementsLabs/open-crm/releases/tag/v1.11.0) (2026-08-28)

This is a small maintenance release. Its one operational change is that
**database backups are now stored on a local Docker volume instead of S3**.
There are no application features, no database migrations and no API changes.

> ⚠️ **Operators must read the Upgrade notes before deploying.** Backups taken
> after this release are written to the new `db-backup-data` volume, not to your
> S3 bucket. The `DB_BACKUP_S3_*` and `DB_BACKUP_AWS_*` variables are no longer
> used.

---

## Changes

### Backups are stored locally

The `db-backup` sidecar now uses its `local` storage backend
(`STORAGE_BACKEND: local`). Dumps go to `/var/lib/db-backup-service` inside
the container, which is mounted on a new named volume, **`db-backup-data`**.
Backups survive container restarts and redeploys, but they now live on the same
host as the database.

The backup interval, the API token shared with the backend and the
`/admin/backup` page all work as before.

### Other changes

- Added the Open CRM logo asset (`frontend/public/open-crm-logo.png`).
- Added design and behaviour docs for spec 118 (version pinning gate) and
  spec 119 (dependency updates), and recorded the follow-ups that were deferred.

---

## Upgrade notes

### Backup storage moved from S3 to a local volume

1. **Before deploying, take a backup** through `/admin/backup` on the running
   v1.11.0 deployment. This backup still goes to S3.
2. **Deploy v1.12.0.** Docker Compose creates the `db-backup-data` volume
   automatically.
3. **Check `/admin/backup`.** It should report the sidecar as healthy, and a
   newly triggered backup should appear in the list.

Keep in mind:

- **Existing S3 backups are not migrated.** They stay in the bucket, and the
  backup service no longer lists or restores them. Keep the bucket until you no
  longer need those dumps.
- **No off-host copy is made any more.** If the host or its disk is lost, the
  backups are lost with it. If you need off-site backups, copy the
  `db-backup-data` volume elsewhere yourself.
- **The `DB_BACKUP_S3_BUCKET`, `DB_BACKUP_S3_ENDPOINT`, `DB_BACKUP_S3_PREFIX`,
  `DB_BACKUP_AWS_ACCESS_KEY_ID`, `DB_BACKUP_AWS_SECRET_ACCESS_KEY` and
  `DB_BACKUP_AWS_DEFAULT_REGION` variables are no longer read.** You can remove
  them from your deployment environment.

### Nothing else to do

No Flyway migrations, no new services and no new routes. Rolling back to
v1.11.0 only means redeploying the old tag; after that, backups go to S3 again.
